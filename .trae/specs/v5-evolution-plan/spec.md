## 一、演进背景

### 1.1 V1-V4 已建立的能力基座

| 维度 | V1-V3 已有 | V4 新增 | V5 起点 |
|---|---|---|---|
| 文件处理 | 上传/解析/检索/分析/画像/报告全闭环 | - | 文件全生命周期完整 |
| AI 能力 | NER + YARA 静态分析 | LLM 抽象 + 4 项 AI 辅助（摘要/推理/NL搜索/草稿） | LLM 基座就位 |
| 安全合规 | RBAC + 基本审计 | 脱敏 + 分级访问 + 细粒度审计 + 限流 | 合规四件套就位 |
| 协同工作流 | 任务 + 通知 | 工作流引擎 + 评审 + 协同标注 | 工作流基座就位 |
| 情报互通 | IOC 内部闭环 | STIX 导出 + TAXII Server | 标准化输出就位 |
| 数据底座 | PostgreSQL + ES + Milvus + Neo4j + MinIO | + Redis（限流） | 多模存储完整 |

### 1.2 V5 核心问题

V4 后平台已具备"AI 辅助的红方协作分析平台"基本形态，但存在三大演进瓶颈：

1. **AI 仍是"辅助"而非"自主"**：V4 AI 是单轮 Prompt→Response，无法多步推理、调用工具、自主决策。红方分析师仍需驱动每一步
2. **分析维度单一**：仅静态分析（NER/YARA/LLM 摘要），缺动态行为分析、多模态融合、主动狩猎
3. **生产化能力薄弱**：可观测性、多租户、国产化适配均未启动，难以规模化部署

### 1.3 V5 战略主题

**从"AI 辅助"升级为"AI 自主分析 + 全维度威胁感知 + 生产级平台"**

## 三、V5 子迭代规划

### V5.1 — AI Agent 化（P0，核心差异化，4 周）

**目标**：将 V4 的"单轮 AI 辅助"升级为"AI Agent 自主分析"

#### 关键能力

1. **RAG 知识库**
   - 引入向量库扩展（Milvus 已有，新增知识库 collection）
   - 红方知识库种子：ATT&CK 矩阵 + CVE 漏洞库 + APT 组织档案 + 历史分析报告
   - 文件解析后自动向量化入库，构建"文件-知识"双向检索

2. **Agent 工具链（Function Calling）**
   - Agent 可调用工具：`search_files` / `get_threat_intel` / `run_ner` / `query_neo4j` / `generate_report`
   - 工具协议：基于 LLM Function Calling 标准（兼容 OpenAI / Ollama 工具调用格式）
   - 工具注册中心：`ToolRegistry`，支持动态注册与权限校验

3. **多步推理引擎**
   - 实现 `AgentExecutor`：Plan → Act → Observe → Reflect 循环
   - 最大步数限制（默认 10 步）+ 总 token 预算控制
   - 推理轨迹可视化（前端展示 Agent 思考链路）

4. **自主分析任务**
   - 用户输入"分析这个文件是否 APT28 攻击样本" → Agent 自主检索情报 + NER + 图谱查询 + 生成结论
   - 分析任务异步执行 + 进度推送（WebSocket）
   - 任务结果含：结论 + 证据链 + 引用文件 + 置信度

#### 新增微服务

- 无新增微服务，扩展 `ai-service`（新增 `agent/` 包）

#### 关键交付

| # | 交付物 | 类型 |
|---|---|---|
| 1 | `RagService` + 知识库 collection 设计 | 后端 |
| 2 | `ToolRegistry` + 6 个内置工具 | 后端 |
| 3 | `AgentExecutor`（ReAct 模式） | 后端 |
| 4 | `AutonomousAnalysisService` | 后端 |
| 5 | `POST /api/ai/agent/analyze` 端点 | 后端 |
| 6 | 前端「Agent 分析」任务页（任务列表 + 推理轨迹可视化） | 前端 |
| 7 | 前端「知识库管理」页面（上传文档 / 检索测试） | 前端 |
| 8 | 单元测试 ≥ 15 用例 | 测试 |

### V5.2 — 沙箱动态分析（P1，分析能力补齐，3 周）

**目标**：从"静态分析"扩展到"动态行为分析"，覆盖可疑样本的运行时行为

#### 关键能力

1. **Cuckoo 沙箱集成**
   - 后端：`CuckooClient`（REST API 调用 Cuckoo Sandbox）
   - 任务提交：可疑文件 → Cuckoo 提交 → 轮询结果
   - 结果解析：进程行为 / 网络连接 / 文件操作 / 注册表修改 / API 调用

2. **行为指标提取**
   - 进程树 → STIX Process 对象
   - 网络连接 → STIX NetworkTraffic + IOC 提取
   - 文件操作 → 文件系统变更清单
   - API 调用 → ATT&CK 技术映射

3. **分析任务编排**
   - analyze-service 新增 `DynamicAnalysisService`
   - 静态分析（NER/YARA）+ 动态分析（Cuckoo）联合编排
   - 任务状态机：PENDING → SUBMITTED → RUNNING → COMPLETED → PARSED

4. **前端动态分析视图**
   - 文件详情页新增「动态分析」Tab
   - 进程树可视化（树形组件）
   - 网络拓扑图（关系图组件）
   - ATT&CK 技术热力图

#### 新增依赖

- Cuckoo Sandbox（独立部署，HTTP API 调用）
- 无新增 Java 依赖（用 RestTemplate）

#### 关键交付

| # | 交付物 | 类型 |
|---|---|---|
| 1 | `CuckooClient` + 配置 | 后端 |
| 2 | `DynamicAnalysisService` + 任务编排 | 后端 |
| 3 | `BehaviorIndicatorExtractor`（行为→STIX/ATT&CK） | 后端 |
| 4 | `POST /api/analyze/dynamic/submit` 端点 | 后端 |
| 5 | 前端「动态分析」Tab + 进程树 + 网络拓扑 | 前端 |
| 6 | 单元测试 ≥ 10 用例（Cuckoo mock） | 测试 |

### V5.3 — 威胁狩猎（P1，主动防御，3 周）

**目标**：从"被动分析上传文件"扩展到"主动狩猎威胁"

#### 关键能力

1. **ATT&CK 矩阵导航**
   - 引入 ATT&CK 矩阵数据集（14 战术 × 193 技术）
   - 前端 ATT&CK 矩阵热力图（基于平台已分析文件标记的技术）
   - 点击技术 → 显示相关文件 / IOC / 历史分析

2. **狩猎假设（Hypothesis）**
   - 用户创建狩猎假设："假设攻击者使用 T1059 命令执行"
   - 系统自动检索：含该技术指标的文件 / 实体 / 网络连接
   - 假设验证结果：命中清单 + 置信度 + 推荐 IOCs

3. **检测规则管理**
   - Sigma 规则导入 / 编辑 / 测试
   - YARA 规则版本管理 + 命中统计
   - 规则与 ATT&CK 技术双向关联

4. **狩猎工作流**
   - 工作流引擎（V4 复用）编排：假设 → 检索 → 验证 → 报告
   - 狩猎任务可触发 V4 工作流评审

### V5.4 — 可观测性体系（P2，生产化基础，2 周）

**目标**：建立全链路可观测性，支撑生产部署与故障排查

#### 关键能力

1. **OpenTelemetry 全链路追踪**
   - 12 个微服务接入 OTel SDK
   - 跨服务 Trace 传播（HTTP Header / Kafka Header）
   - Trace UI：Jaeger 部署 + 前端集成查看

2. **Prometheus 指标体系**
   - 业务指标：文件解析成功率 / AI 调用延迟 / 工作流审批时长
   - 系统指标：JVM / DB 连接池 / Kafka lag / Redis 命中
   - Grafana Dashboard 模板：服务总览 / AI 服务 / 工作流 / 数据库

3. **告警体系**
   - AlertManager + 飞书 Webhook 告警（复用 V3 SlackWebhookService）
   - 告警规则：错误率 > 5% / AI 降级触发 / 限流触发 / Kafka 积压
   - 告警分级：P0（电话）/ P1（飞书加急）/ P2（飞书普通）

4. **结构化日志统一**
   - 统一 JSON 日志格式（timestamp/level/traceId/service/msg/fields）
   - ELK / Loki 集中日志（部署文档）

## 六、已决策项（用户 2026-07-31 确认）

### 6.1 P0 决策：V5 主线方向 → ✅ 方案 A

**V5 聚焦 D1（AI Agent）+ D2（沙箱）+ D3（威胁狩猎）+ D4（可观测性）四线齐进，13 周完成。**

### 6.2 P1 决策：V4 收尾 vs V5 启动 → ✅ 方案 A

**先 V4.7 收尾 2 周达到 95+ 通过线，再启动 V5。**

V4.7 必交付范围：
- P0：Task 6 前端 AI 集成 + SubTask 8.5 密级标识 + SubTask 2.4/11.6 Kafka 集成 + Task 23 V4 验证报告
- P1：Task 14 工作流设计器 + SubTask 12.4/12.5 评审区域 + SubTask 13.4 WS 客户端 + SubTask 7.4 脱敏规则管理页
- P2（MISP 归属）：Task 17 MISP 集成（见 6.3）

### 6.3 P2 决策：MISP 集成归属 → ✅ 方案 B

**MISP 集成归 V4.7 收尾时一并完成（属于 V4.4 情报互通闭环）。**

理由：MISP 与已交付的 STIX/TAXII 是配套能力，归 V4.4 闭环更合理，避免 V5 主题被情报互通遗留干扰。
