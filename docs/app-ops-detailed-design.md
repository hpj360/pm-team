## 2. D1 数据空间资产台账

路由：`/ops/data/spaces` ｜ 负责人：平台管理员 ｜ 受众：平台管理员、空间负责人

### 2.1 定位与价值

把"团队空间"从配置项升级为可运维资产。解决三大痛点：
1. 空间无生命周期管理，离职产生孤儿空间
2. 空间健康度不可见，问题空间难发现
3. 配额变更无历史，审计困难

### 2.2 用户故事

- 作为**平台管理员**，我想看到所有空间的健康分排行，以便优先处理问题空间
- 作为**平台管理员**，我想把离职人员负责的空间移交，避免孤儿空间
- 作为**空间负责人**，我想看到自己空间的资产概览与配额趋势
- 作为**安全工程师**，我想筛查处于"冻结/归档"状态的空间，确认权限已收敛

### 2.3 功能清单

| 编号 | 功能 | 说明 |
|------|------|------|
| D1-F1 | 空间列表 | 分页/筛选/排序/批量；支持按健康分/配额/状态筛选 |
| D1-F2 | 空间详情 | 6 个 Tab：概览/文件分布/链路健康/成员/配额历史/操作事件 |
| D1-F3 | 创建空间 | 名称/编码/负责人/配额/生命周期策略 |
| D1-F4 | 生命周期状态机 | active→frozen→archived→destroyed，状态变更需工单 |
| D1-F5 | 负责人移交 | 选择新负责人 → 通知确认 → 移交记录留痕 |
| D1-F6 | 空间健康分 | 0–100 分，含失分项明细与改进建议 |
| D1-F7 | 配额变更 | 调整存储/文件数配额，需工单审批 |
| D1-F8 | 批量操作 | 批量冻结/归档（需工单） |

### 2.4 页面布局

**列表页**：
```
┌─ 筛选条：关键词 | 状态 | 健康分区间 | 负责人 ──── 右侧：批量操作 ▾ ┐
├─ KPI 带：空间总数 | 异常数 | 健康分均值 | 即将满配额数 ──────────┤
├─ 表格列：空间 | 编码 | 负责人 | 文件数 | 存储用量(配额%) | 健康分 | 状态 | 操作 ┤
│         操作：详情 | 冻结 | 移交 | 销毁(高危)                       │
└─ 分页 ───────────────────────────────────────────────────────┘
```

**详情页 Tab**：
- 概览：基础信息卡 + 健康分仪表盘 + 配额使用率 + 近 7 天上传趋势
- 文件分布：按 file_type 饼图 + 按存储层（热/冷/归档）条形图
- 链路健康：四阶段成功率 + 索引积压 + 解析积压（数据来自监控）
- 成员：成员列表 + 角色 + 最近活跃 + 移除（需工单）
- 配额历史：配额变更时间线（含量/时间/操作人/工单号）
- 操作事件：该空间所有 `OPS_*` 事件流（来自 t_file_event）

### 2.5 核心交互流程

**空间销毁流程（高危）**：
```
点击销毁 → 弹窗显示影响（文件数/存储量）→ 强制输入空间编码确认
  → 提交高危工单（24h 撤回窗口）→ 工单审批（负责人+管理员双签）
  → 身份二次验证（飞书扫码）→ 执行：四存储联动删除（PG/MinIO/ES/Neo4j/Milvus）
  → 写入 OPS_DELETE_FILE 事件 → 工单验证 → 空间状态=destroyed
异常分支：
  - 撤回窗口内撤回 → 工单关闭，空间恢复 active
  - 删除部分失败 → 标记 partial_destroyed，触发 P1 告警，转人工
  - 身份验证失败 3 次 → 锁定操作 1h，告警
```

**生命周期状态机**：
```
active ──冻结──→ frozen ──归档──→ archived ──销毁──→ destroyed
  ↑               │                  │
  └──解冻────────┘                  │
  ↑                                  │
  └──恢复(archived→active)──────────┘
```
- frozen：禁止上传/修改，只读
- archived：文件转冷存储，索引保留，访问需恢复
- destroyed：软删除 30 天后物理清除

## 3. D2 数据一致性对账中心

路由：`/ops/data/consistency` ｜ 负责人：数据治理 ｜ 受众：数据治理、SRE

### 3.1 定位与价值

文件管理系统的"数据腐化检测器"。多存储（PG/MinIO/ES/Neo4j/Milvus）长期运行必然产生不一致，对账中心是发现这些不一致的唯一手段。价值：
1. 提前发现数据丢失，避免用户搜不到文件
2. 量化数据腐化率，驱动存储质量改进
3. 为治愈操作台提供待修复清单

### 3.2 用户故事

- 作为**数据治理**，我想每天自动对账，发现不一致立即告警
- 作为**数据治理**，我想看到某空间哪些文件在 ES 搜不到，并一键发起重索引
- 作为**SRE**，我想看到 trace 断链的文件，定位链路异常
- 作为**空间负责人**，我想收到"你的空间有 3 个文件数据不一致"的通报

### 3.3 功能清单

| 编号 | 功能 | 说明 |
|------|------|------|
| D2-F1 | 对账任务管理 | 8 类对账任务配置（频率/阈值/范围） |
| D2-F2 | 手动触发 | 按空间/类型手动跑对账 |
| D2-F3 | 对账结果列表 | 任务名/上次执行/状态/不一致数/趋势 |
| D2-F4 | 不一致明细 | 按空间分组，列出 file_id/差异类型/发现时间/建议操作 |
| D2-F5 | 一键修复 | 对可自动修复项发起治愈工单（联动 D3） |
| D2-F6 | 对账报告 | 每日报告，含不一致趋势 Top 空间 |
| D2-F7 | 对账规则配置 | 自定义对账 SQL/查询条件 |

### 3.4 页面布局

```
┌─ KPI：今日任务数 | 不一致数 | 已修复数 | 待处理数 | 腐化率(‱) ─┐
├─ Tab：对账总览 | 不一致明细 | 任务配置 | 报告 ──────────────────┤
│  对账总览：8 类任务卡片（状态/上次执行/不一致数/趋势 mini 图）  │
│  不一致明细：左侧任务树 + 右侧明细表（file_id/类型/空间/建议）   │
│            顶部：批量发起修复工单                              │
└─ 分页 ─────────────────────────────────────────────────────┘
```

### 3.5 核心交互流程

**对账任务执行流程**：
```
定时触发/手动触发 → 任务入队（按 team_space 分批）
  → 分批扫描（游标分页，每批 1000，避免大表 OOM）
  → 差异写入 t_consistency_check_diff（前 100 条样本 + 完整报告存 MinIO）
  → 更新 t_consistency_check 汇总
  → 不一致数 > 0 → 触发告警 + 通知空间负责人
  → 一键修复 → 转工单（D3 治愈）
异常分支：
  - 单空间对账超时(>10min) → 标记 timeout，跳过，继续下一空间
  - 存储不可达 → 标记 failed，告警，不阻塞其他任务
  - 差异数 > 10000 → 仅存样本 + 触发 P1 告警（疑似大规模故障）
```

**对账分批策略**（解决大表性能问题）：
- 按 `team_space_id` 分片，每空间独立对账
- 空间内按 `file_id` 游标分页（`WHERE file_id > ? ORDER BY file_id LIMIT 1000`）
- ES 侧用 `search_after` 替代 from/size
- 对账任务支持断点续跑（记录 `last_file_id`）
- 大空间（>100 万文件）拆分为多子任务并行

### 3.6 数据模型

见上游 §5.2.3 `t_consistency_check`。新增明细表：

```sql
CREATE TABLE t_consistency_check_diff (
  id              BIGINT PRIMARY KEY,
  check_id        BIGINT NOT NULL COMMENT '对账任务ID',
  team_space_id   BIGINT NOT NULL,
  file_id         BIGINT COMMENT '文件ID(若适用)',
  object_key      VARCHAR(512) COMMENT '对象键(MinIO对账)',
  diff_type       VARCHAR(32) NOT NULL COMMENT 'PG_MISSING/MINIO_MISSING/ES_MISSING/ES_ORPHAN/TRACE_BROKEN/...',
  detail          JSONB COMMENT '差异详情(前后值)',
  suggested_action VARCHAR(32) COMMENT 'REINDEX/REPARSE/PURGE_ORPHAN/MANUAL',
  status          SMALLINT DEFAULT 0 COMMENT '0待处理 1已修复 2已忽略',
  found_at        TIMESTAMP DEFAULT NOW(),
  fixed_at        TIMESTAMP
);
CREATE INDEX idx_diff_check_space ON t_consistency_check_diff(check_id, team_space_id, status);
```

### 3.8 边界 case

| 场景 | 处理 |
|------|------|
| 对账期间文件正在变更 | 标记"快照时间点"，差异复核窗口 5min，避免假阳性 |
| 差异数爆炸（>1 万） | 仅存样本，触发 P1，疑似存储故障 |
| ES 索引重建中 | 跳过 ES 对账，标记"维护中" |
| 跨存储时间差 | 接受 1min 内的最终一致，不报差异 |
| 对账任务并发同空间 | 分布式锁 `lock:check:{space}:{type}`，互斥 |

| TC-D2-06 | 差异 >1 万 | 仅存样本 + P1 告警 |

## 4. D3 数据链路治愈操作台

路由：`/ops/data/heal` ｜ 负责人：SRE/数据治理 ｜ 受众：SRE、数据治理、空间负责人（本空间）

### 4.1 定位与价值

### 4.5 核心交互流程

**批量重解析流程**：
```
选择"批量重解析" → 筛选目标（如 error_code=PARSE.TIMEOUT）
  → 预览影响（120 文件，8min，中风险）
  → 文件数 > 50 → 必须走工单
  → 发起工单：类型=REPARSE，目标=file_id[]，参数={reset_status:true}
  → 审批（数据治理→平台管理员）
  → 执行：异步任务，文件级分布式锁 lock:file:{id}
    → 每个文件：清空 parseStatus → 入队 → 写 OPS_RETRY_PARSE 事件
    → 进度实时更新（已完成/总数）
  → 验证：检查 parseStatus=2 比例
  → 验证通过 → 工单完成；失败 → 标记失败项，可部分重试
异常分支：
  - 文件已被删除 → 跳过，记录 SKIPPED
  - 解析再次失败 → 记录 FAILED + 错误码，不阻塞其他文件
  - 任务中断 → 支持断点续跑（记录 last_file_id）
  - 并发治愈同文件 → 分布式锁拒绝，提示"正在治愈中"
```

**免审批操作的频率限制**：
- 单用户单接口 10 次/min
- 超限返回 429 + 告警事件
- 防止脚本滥用免审批通道

### 5.5 核心交互流程

**冷热分层流程**：
```
定时任务(每日 03:00) → 扫描各空间符合"转冷"条件文件
  → 批量迁移 MinIO 对象到归档桶（生命周期规则 + PG 标记 storage_tier=cold）
  → 写 OPS_ARCHIVE 事件
  → 更新空间 cold_file_count
异常分支：
  - MinIO 迁移失败 → 重试 3 次，仍失败标记 P2 告警
  - 文件正在被访问 → 跳过，下次再处理
```

**过期清理流程（高危）**：
```
定时任务(每日 04:00) → 标记过期文件（lifecycle_status=pending_destroy）
  → 生成清理工单（含文件数/体积）
  → 审批（空间负责人→平台管理员）
  → 24h 撤回窗口
  → 执行：四存储联动删除
  → 验证：各存储确认删除
异常分支：
  - 撤回 → 恢复 lifecycle_status=active
  - 部分删除失败 → 标记 partial_destroyed，告警
```

**归档恢复流程**：
```
用户访问归档文件 → 提示"已归档，需恢复" → 点恢复
  → 异步任务：MinIO 归档桶→热桶 + PG storage_tier=hot
  → 预计耗时提示（按文件大小估算）
  → 完成后通知用户
异常分支：
  - 归档对象已过期清除 → 提示"文件已销毁"
```

- 服务端读取配置时，按 `team_space_id` 判断走灰度版本还是稳定版本
- 灰度比例 = 灰度空间数 / 总空间数
- 灰度切换通过配置中心实时下发，无需重启服务

### 7.5 核心交互流程

**权限回收巡检流程**：
```
定时任务(每日 06:00) → 扫描离职成员（HR 系统对接或手动标记）
  → 扫描过期分享链接
  → 扫描"角色>实际需要"成员（如 OWNER 但 30 天未登录）
  → 生成清理清单
  → 批量清理（移除成员/失效链接）→ 写审计
  → 通知空间负责人
异常分支：
  - 离职成员是空间唯一 OWNER → 不清理，告警要求先移交
  - 清理失败 → 重试，仍失败告警
```

**异常下载检测流程**：
```
实时流（消费 t_file_event 的 DOWNLOAD 事件）
  → 规则引擎：
    - 单用户 1h 内下载 > 500 文件
    - 单用户 1h 跨 > 3 空间下载
    - 非工作时间大批量下载
  → 命中规则 → 触发 P1 告警 + 飞书通知安全工程师
  → 可选：临时冻结该用户下载权限（需安全工程师确认）
```

**数据导出审批流程**：
```
空间负责人发起导出 → 选择范围（整空间/文件夹/筛选条件）
  → 系统评估数据量 + 敏感等级
  → 提交工单（安全工程师审批）
  → 审批通过 → 异步生成导出包（含水印：用户ID+时间）
  → 导出包存 MinIO，7 天有效，下载链接通知申请人
  → 记录导出审计
异常分支：
  - 导出含高敏感文件 → 强制安全工程师+平台管理员双签
  - 导出包生成失败 → 重试，通知
```

|------|------|---------|------|
| D1 | D7 | 健康分供报告 | 数据查询 |
| D1 | 工单 | 状态变更/配额/销毁 | 触发工单 |
| D1 | 告警 | 健康分下降 | 告警事件 |
| D2 | D3 | 不一致一键修复 | 转治愈工单 |
| D2 | D7 | 腐化率入报告 | 数据查询 |
| D2 | 告警 | 不一致数 > 0 | 告警事件 |
| D3 | D1 | 治愈事件回流 | t_file_event |
| D3 | D7 | 治愈成功率入报告 | 数据查询 |
| D3 | 工单 | 批量/高危操作 | 触发工单 |
| D4 | D1 | 配额/冷文件更新 | 数据更新 |
| D4 | D7 | 容量趋势入报告 | 数据查询 |
| D4 | 工单 | 过期清理/扩容 | 触发工单 |
| D5 | D3 | 标签变更触发重打标 | 治愈操作 |
| D5 | 工单 | 高危变更 | 触发工单 |
| D6 | D1 | 权限清理更新成员 | 数据更新 |
| D6 | D3 | 重打标执行 | 治愈操作 |
| D6 | 工单 | 导出审批 | 触发工单 |
| 告警 | D3 | 告警"转治愈" | 跳转 |
| 告警 | D7 | 异常通报 | 飞书推送 |
| 工单 | 全模块 | 工单执行验证 | 状态回调 |

**核心数据流**：
```
D2 对账发现问题 ──→ D3 治愈执行 ──→ t_file_event 留痕
       │                ↓                  
       │             工单审批(批量)         
       ↓                                  
D7 报告(含建议) ──→ 用户点击建议 ──→ 工单 ──→ D3 执行
```
